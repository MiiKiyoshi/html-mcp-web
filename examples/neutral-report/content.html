A nightly suite of 2,140 tests runs on eight runners and is finished only when its slowest runner is. Splitting the tests by file name gave one runner the whole integration folder, and the suite took 74 minutes while another runner sat idle after 18. Since 15 September the suite splits its tests by measured duration instead of by file name. It now finishes in 47 minutes instead of 74. We describe the split, the measurements behind it, and the two kinds of test that still fall back to the old split.

The nightly suite checks every change merged during the day before the next morning's release candidate is cut. Its finishing time sets how early that candidate can be cut, and every minute the suite runs past the start of the working day is a minute in which a failure found overnight cannot yet be fixed.

The suite is finished when its slowest runner is. The total test time does not change with the split, so a split that leaves one runner with much more work than the others makes the whole suite wait for that runner. Splitting by file name did exactly that: the integration tests sit in one folder, and their file names sort them onto the first runner.

This note makes three points. First, the old split put 74 minutes of work on one runner and 18 on another. Second, a greedy split by measured duration, the longest-first rule graham1969, brings every runner within two minutes of the others. Third, new tests and reruns still bypass the split, and we describe the fixes that go in next.

The scheduler reads each test's median duration over the last seven nightly runs. It sorts the tests from longest to shortest and places each one on the runner with the least total time so far, until every test has a runner. Let $t_i$ be the median duration of test $i$ and $T_r$ the total time placed on runner $r$. Each test goes to

$$r^\ast = \arg\min_{r} T_r, \qquad T_{r^\ast} \leftarrow T_{r^\ast} + t_i.$$

The median over seven runs rather than the last run keeps one slow night, such as a night with a congested network, from moving a test to another runner. A test that failed in one of the seven runs keeps its duration, since a failing test still occupies its runner for that long.

What Stayed the Same

The same eight runners run the same 2,140 tests. The order of tests within a runner, the retry rule, and the report format are unchanged. Only the assignment of tests to runners differs, so a failure seen under the new split points at the same test it would have pointed at before.

We compare the nightly runs of 8 to 14 September, split by file name, with those of 15 to 21 September, split by duration. Table 1 gives each runner's median finishing time over the seven nights of each week.

The total test time is 368 minutes both ways, since only the split changed. Runners that used to finish early now take more of the work, and the suite ends when runner 1 does, 27 minutes sooner. The spread between the first and the last runner to finish fell from 56 minutes to 2.

The longest-first rule is not optimal in general, but its result is at most a third longer than the best possible split graham1969. Here the longest single test takes 9 minutes, under a fifth of a runner's share, which leaves the rule little room to err: the best split cannot end before 46 minutes, the total divided by eight, and ours ends at 47.

Two kinds of test still fall back to the old split.

New Tests

A test added this week has no recorded duration, so it is placed by file name. Until it has seven runs, we will give it the median of the other tests in its folder.

Reruns After a Flaky Failure

A rerun goes back to the runner that failed, which already has its full share. We will send reruns to the spare ninth runner instead.
